Claude Code é worker sob demanda (B) — sua hipótese está certa nesse ponto. Mas o executor não pode chamá-lo de fora: não existe credencial no ambiente para isso. O wake-up tem de ser auto-agendado de dentro da plataforma Claude, com o SQL barato como primeiro portão dentro da sessão.

01 A pergunta crítica, respondida com evidência

Sim, dá para acordar o Claude Code programaticamente. Não é teoria — você já faz isso. Encontrei 6 Routines (triggers) na sua conta, todos created_via: meta_mcp, todos com ended_reason: run_once_fired e last_fired_at preenchido. Dispararam de verdade.

MecanismoExiste?Serve de piloto automático?
CCR Routines

claude -p headless no container Roda Não. Testei: funciona, mas sem nenhum MCP. Sem Supabase não há GPS, claim nem deploy.
CronCreate (tool do harness) Inviável Não. A própria doc diz: vive só na sessão, some quando o Claude sai, durable não tem efeito, expira em 7 dias, e só dispara com o REPL ocioso.
A refutação — seta invertida

A arquitetura candidata é GPS → scheduler barato → executor → invoca Claude Code. Esse último passo não é executável hoje:

  • create_trigger e fire_trigger são ferramentas MCP disponíveis dentro de uma sessão Claude. Não achei endpoint REST que um edge function pudesse chamar.
  • No container: ANTHROPIC_API_KEY ausente, ANTHROPIC_AUTH_TOKEN ausente, CLAUDE_CODE_OAUTH_TOKEN ausente, nenhum token CCR. A autenticação é por oauthAccount via proxy local 127.0.0.1:39229 — inalcançável de um edge function.

Um pg_cron no Supabase não tem com o que acordar o Claude. Se desenhássemos o piloto automático assumindo essa seta, ele não sairia do papel.

Como salvar a arquitetura

Inverta a direção. Em vez de o executor acordar o Claude, uma Routine com sessão nova por disparo se acorda sozinha e a primeira coisa que faz é chamar o SQL determinístico. Sem trabalho, encerra em segundos. A propriedade de custo se preserva sem depender de uma capacidade que não existe.

02 Papel correto do Claude Code

B — WORKER SOB DEMANDA. Fundamentado por quatro fatos do ambiente real, não por preferência:

  • Persistência. O container é efêmero e reciclado por inatividade. Nada que more só nele sobrevive. CronCreate morre junto. Não há o que sustente um orquestrador permanente.
  • Custo de partida a frio. Medi: claude -p para responder "OK" gastou 38.091 tokens de escrita de cache e US$ 0,23. A segunda chamada, com cache quente, US$ 0,083. Todo despertar paga esse pedágio antes de fazer qualquer trabalho.
  • Rate limit é a escassez real. get_session devolve rateLimitType: "five_hour". Sessão de Claude Code consome janela de assinatura, não fatura por token. Um orquestrador permanente competiria com o seu uso interativo — a conta não é em dólares, é em você não conseguir trabalhar.
  • Credenciais. O que dá poder à sessão são os conectores MCP de organização (Supabase e Google Drive aparecem connected: true), não variáveis no container. Isso é uma vantagem — e é exatamente o que o claude -p headless não herda.

Claude Code é excelente como engenheiro convocado: já chega com Supabase MCP, git autenticado, deploy de edge function e migration. É péssimo como relógio.

03 Mecanismo real de wake-up

   │  cron mínimo: 1×/hora · sessão nova a cada disparo
   ▼
Sessão Claude nasce  ─ herda conectores MCP da organização
   │
   ├─ PASSO 1 (segundos): select fn_gps_panorama()

   │
   └─ há trabalho? claim → executa → evidência → finaliza → encerra

Canal de retorno = BANCO, não a API de sessão.
Limitação confirmada — e você já a documentou

Uma sessão-mãe só enxerga o status da filha, nunca o transcript. Está escrito num dos seus próprios triggers: "o conteúdo do transcript da filha só é visível na UI — eu só enxergo o status". Portanto o resultado não volta pela API. A sessão trabalhadora precisa escrever o desfecho no banco (frentes.evidencia, executor_ticks), e o banco é o canal de retorno. É o que o seu fluxo atual já faz na prática.

05 Caso 2 — espera, shadow e amostra orgânica

O fluxo candidato — trabalho → registrar espera → release → watcher barato → condição satisfeita → fechar espera → GPS volta a marcar acionável — é suportado pela arquitetura atual, com uma lacuna importante.

O que já funciona: frentes_espera é append-only, tem tipo='evento_organico', e vw_frentes_elegiveis deriva acionavel = elegivel E sem espera aberta. Fechar a espera devolve a frente ao GPS automaticamente, sem tocar em nada mais. O desenho está certo.

E a distinção que você fez está corretamente refletida no schema: fechar espera grava evidencia_encerramento; aprovar critério de aceite é outro ato, em fn_frente_finalizar_chat. Condição de espera satisfeita ≠ critério de aceite aprovado — o banco já separa os dois.

Lacuna que impede o watcher determinístico

frentes_espera tem id, frente_slug, tipo, descricao, aberta_em, aberta_por, encerrada_em, encerrada_por, evidencia_encerramento. Não existe campo de condição legível por máquina. "Aguardar 5 execuções orgânicas" vive em descricao, em prosa.

Um watcher barato não pode avaliar isso — e não tem permissão de tentar: a própria tabela proíbe backfill "por prosa, regex ou LLM". Sem um predicado estruturado, ou o watcher não existe, ou vira um LLM lendo texto a cada tick, que é exatamente o custo que queremos eliminar. Este é o contrato que mais bloqueia o piloto automático. Detalhe na seção 12.

Não vou inventar rollback onde ele não é tecnicamente possível. Para migration, o único caminho honesto é exigir migration compensatória escrita e testada antes de aplicar — e, se ela não existir, classificar RISCO e parar. Isso é regra de política, não mecanismo de undo.

09 Crash e recuperação

Evidência real, do seu próprio histórico

Um dos triggers documenta uma sessão travada: "RUNNING, connected, 46.161 tokens de saída gastos, task_summary 'Checking clock against scheduled check-in', sem ter reivindicado a frente em 18 minutos" — e a instrução de contingência: "mais de ~30 minutos sem progresso verificável… a sessão parece travada".

Ou seja: sessões travam, e hoje quem percebe é você. Esse é um ponto concreto onde você ainda está no loop.

O que já protege sem ninguém: a expiração da lease. Uma sessão morta libera a frente sozinha e grava claim_expirado. Nenhuma frente fica presa para sempre.

O que dá para automatizar sem inventar nada: um watchdog em SQL comparando frentes_claims.heartbeat_em com now(). Heartbeat parado além do limiar = sessão travada, mesmo com status RUNNING. Isso é detectável deterministicamente e **sem LLM** — e é estritamente melhor que o critério atual, que depende de você olhar a tela.

10 Custo comparativo

Duas moedas diferentes, e confundi-las levaria à decisão errada: Claude Code consome janela de rate limit de assinatura; a API Anthropic consome dólares. Preços por MTok: Opus 5 US$ 5/25 · Sonnet 5 US$ 3/15 · Haiku 4.5 US$ 1/5.

ArquiteturaCusto ociosoMoeda / observação
1. Claude Code permanentealto e contínuoQueima janela de 5h competindo com seu uso interativo. Inviável também por persistência — o container morre.
2. Claude Code sob demanda, 1×/h~US$ 0,08–0,23 por tick vazio≈ US$ 60–170/mês só de cold start em ticks sem trabalho. Medido, não estimado.
3. API Anthropic sob demandamenor por chamadaMas não há API key provisionada, e reconstruir Supabase MCP + git + deploy num worker próprio é obra grande sem ganho.
4. Worker determinístico + LLM só para engenharia≈ zeroSQL decide em 186 ms. LLM só entra quando há engenharia de verdade.
5. GitHub Actions para operações padronizadasminutos grátisNão existe .github/workflows hoje — teria de ser criado do zero, e precisaria de secrets próprios.

A consequência prática: mesmo na arquitetura 4, se o despertar for uma Routine horária, cada tick vazio custa o cold start. Por isso o tick precisa ser o mais barato possível — abrir, consultar o SQL, encerrar — e a frequência deve seguir o ritmo real do trabalho, não o do relógio. Um despertar de hora em hora, 24 h por dia, gasta mais em ticks vazios do que em trabalho.

11 Limitações reais (provadas, não supostas)

  1. Edge function não acorda Claude Code. Sem API key, sem token CCR, autenticação por OAuth atrás de proxy local. A seta de fora para dentro não existe hoje.
  2. claude -p headless não tem MCP. Testei: respondeu NENHUM_MCP. Sem Supabase não há GPS, claim nem deploy.
  3. Resultado da sessão filha não retorna pela API — só status. O banco tem de ser o canal.
  4. Intervalo mínimo de Routine é horário. Não dá para reagir em 15 minutos por esse caminho.
  5. Migration não tem undo, e Vercel não é automatizável sem token.
  6. frentes_espera não tem condição legível por máquina — bloqueia o watcher determinístico.
  7. Rate limit de 5 h é compartilhado entre o executor e você.

12 Contrato necessário do GPS

Não alterei nada. Um item novo, mais bloqueante que o da rodada anterior.

Predicado estruturado de espera

Bloqueia o caso 2 inteiro
  • Fato faltante: frentes_espera não tem coluna que expresse a condição de fechamento de forma avaliável por máquina.
  • Por que o executor precisa: sem isso não existe watcher barato. A condição vive em descricao, e a própria tabela proíbe interpretá-la por prosa, regex ou LLM. Sem predicado, todo shadow e toda amostra voltam a depender de alguém lendo texto.
  • Exemplo real: instrumentar-envio-agentes-conversacionais aguarda "o PRIMEIRO outbound orgânico do Bruno posterior à migration". Isso é uma consulta SQL de uma linha — mas hoje só existe como frase.
  • Menor alteração possível (sugestão, não decisão): uma coluna opcional com predicado nomeado e parâmetros, por exemplo {"tipo":"contagem_minima","consulta":"fn_espera_outbound_bruno","minimo":1}, avaliada por uma função whitelist. Espera sem predicado continua válida e simplesmente permanece manual — nada quebra, e o preenchimento é incremental.

Os dois itens da rodada anterior seguem de pé: custódia do claim_token e frentes acionáveis cujo próximo passo é esperar. Este terceiro é o de maior impacto: sem ele, o ciclo autônomo trava toda vez que uma frente precisa aguardar material orgânico — que, pelo panorama, é a situação de 4 das 18 trilhas.

  → fecha esperas, marca "há trabalho", não acorda ninguém

  → primeiro ato: consultar o SQL. Sem trabalho, encerra.

CAMADA 3 — engenharia, Claude Code como worker
  claim → código → teste → deploy sob política → evidência
  → escreve desfecho no BANCO e encerra

Onde você continua no loop, e só aqui: provisionar credenciais deliberadamente não delegadas (API key, token Vercel), abrir as flags allow_* uma vez, definir o teto de orçamento, e decidir quanto da janela de 5 h o executor pode consumir do seu próprio uso. Todas são decisões de proprietário por definição — nenhuma é "manda a próxima".
